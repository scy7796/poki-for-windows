# Reading the iOS accessibility tree reliably from an on-device WDA runner

Notes for PokiCore (WDA 16.15.x, iOS 17-27), from the WDA source on `master`, its changelog and PRs, the Appium docs and pymobiledevice3. Unverified items are marked **unverified**.

## Summary and recommendations

PokiCore today sends `animationCoolOffTimeout: 0, waitForIdleTimeout: 0.5, accessibilityDeadline: 2, activeAppDetectionPoint: "200,420"` and reads `GET /source?format=xml&excluded_attributes=visible,accessible,enabled,index` (`Runner.swift`, `Screen.swift`). That is already most of what Appium recommends. What remains is structural: a snapshot request that has entered XCTest cannot be cancelled, and WDA serialises non-standalone routes behind it.

**Settings to run with (per session, `POST /session/:id/appium/settings`)**

| Setting | Value | Why |
|---|---|---|
| `waitForIdleTimeout` | `0` for reads, `0.5-1` around gestures | `0` makes the swizzled quiescence wait return at once ("Making it to believe it is idling"). It is a global, so flip it per request if gestures want a settle. |
| `animationCoolOffTimeout` | `0` | Skips `fb_waitUntilStableWithTimeout` before `/source` and after gestures. |
| `accessibilityDeadline` | `0`, or `1.0` only for reads of a known-live app | It is a pre-check with `notifyWhenEventLoopIsIdleForApplication:`; an app that never idles fails the read with "did not confirm its main run loop is responsive" and is cached as unresponsive for the deadline window. It does not bound the snapshot itself. Needs WDA >= 16.14.1 (WebKit crash fix, #1293). |
| `snapshotMaxDepth` | `30-40` (default 50) | Bounds tree size and memory; web pages and WeChat go deep. Measure how many elements are lost. |
| `snapshotMaxChildren` | `200-500` (default `INT_MAX`) | Caps siblings per node; feeds and banners have many. |
| `includeCustomActionsInPageSource` | `false` (default) | Custom actions cost an AX round-trip per element. JSON `/source` always resolves them; XML only on request. |
| `defaultActiveApplication` | bundle id of the app Poki is driving when known | Removes active-app detection (one more snapshot) from each read. |
| `screenshotQuality` | `1` or `2` | Smaller `/screenshot` payloads; it is standalone and not queued. |

**Order of changes to try**

1. Keep XML `/source` with `excluded_attributes=visible,accessible` (the two attributes that need per-element AX work); add `snapshotMaxDepth`/`snapshotMaxChildren` and check element loss on JD.com, WeChat, Settings.
2. Set `waitForIdleTimeout` to `0` for the read path and only raise it for the gesture that just happened (WDA restores overrides even when quiescence throws since 16.13.6).
3. Drop `accessibilityDeadline` to `0` on the two animated screens and compare: if reads now succeed, the deadline, not the snapshot, was the failure. Keep it on for screens that genuinely hang.
4. Add a `maxDepth`-reduced retry: on a `/source` timeout, do not re-issue the same request (it queues behind the first, which XCTest keeps processing); wait for `/status` to answer, then retry with `snapshotMaxDepth` halved and `scope` set to the active app.
5. Never `POST /session` while `busyWith` is set; WDA session creation kills the old session and waits up to 35 s for teardown. Reuse the session and prefer sessionless routes (`/source`, `/screenshot`, `/wda/activeAppInfo` all accept no session).
6. Launcher: keep the testmanagerd control session alive for as long as the runner must live; treat its drop as fatal and relaunch. There is no documented reconnect.
7. Measure: per read, time for `/source`, element count, depth reached, whether `accessibilityDeadline` fired (error text), and the 60 s `kAXErrorIPCTimeout` signature in the device log.

## 1. WDA settings and endpoints that affect snapshot time and idle waiting

Defaults from `FBConfiguration.m` (`resetSessionSettings`) and the Appium settings reference.

- `waitForIdleTimeout` (float, 10 s). `XCUIApplicationProcess+FBQuiescence.m` swizzles `waitForQuiescenceIncludingAnimationsIdle:` (and the `isPreEvent:` variant); below `DBL_EPSILON` it logs "Quiescence checks are disabled ... Making it to believe it is idling" and returns; otherwise it runs the original inside `withApplicationStateTimeout:`. Also a session capability.
- `animationCoolOffTimeout` (float, 2 s). Used by `FBXPath waitUntilStableWithElement:` before building `/source` and after gestures, via `fb_waitUntilStableWithTimeout:` which temporarily sets `waitForIdleTimeout` and calls `fb_waitForQuiescenceIncludingAnimationsIdle:YES`. `0` skips it.
- `accessibilityDeadline` (float, 0 = off; WDA 16.8.0, PR #1214, also a capability). Swizzles `-[XCAXClient_iOS requestSnapshotForElement:attributes:parameters:error:]`; before the real request it calls `notifyWhenEventLoopIsIdleForApplication:reply:` and waits on a semaphore for the deadline. Failure text: "The application with process identifier %d did not confirm its main run loop is responsive within %.1f second(s)". Per-PID unresponsive cache makes retries fail fast within the window. Reviewer KazuCocoa noted it bounds only the pre-check; the snapshot itself still has no timeout. 16.14.1 skips it for `com.apple.WebKit.*` processes after it crashed WebContent (#1290).
- `snapshotMaxDepth` (int, 50, range 1-62) and `snapshotMaxChildren` (int, `INT_MAX`, since 11.4.0). Applied through `XCAXClient_iOS+FBSnapshotReqParams.m`, which swizzles `-[XCAXClient_iOS defaultParameters]` and `-[XCTElementQuery snapshotParameters]` and merges `maxDepth`/`maxChildren` into XCTest's own parameter dictionary (XCTest defaults: `maxDepth` 2147483647, `maxChildren` 2147483647, `maxArrayCount` 2147483647, `traverseFromParentsToChildren` YES, `snapshotKeyHonorModalViews` NO).
- `customSnapshotTimeout` / `snapshotTimeout`: removed in WDA 9.0.0 (2025-01-16). Not available in 16.x.
- `enforceCustomSnapshots` (bool, false; 10.5.0): forces WDA's private-API snapshot path for everything; slower, more memory.
- `elementResponseAttributes` (`type,label`), `useFirstMatch` (false), `boundElementsByIndex` (false): affect find-element responses only, not `/source`.
- `defaultActiveApplication` (`auto`) and `activeAppDetectionPoint` (20 %/20 % of the screen): `fb_activeApplicationWithDefaultBundleId:` snapshots the AX element at the point to pick among active apps; a known bundle id short-circuits that.
- `includeHittableInPageSource`, `includeNativeFrameInPageSource`, `includeMinMaxValueInPageSource`, `includeCustomActionsInPageSource`, `includeNativeAccessibilityElementInPageSource` (all false): each adds attributes to XML; `hittable` forces a native snapshot.
- `maxTypingFrequency` (60), `useClearTextShortcut` (true), `respectSystemAlerts` (false): not on the read path.
- `includeNonModalElements`, `useUIAutomation`, `waitForQuiescence`: not in current WDA settings or Appium capabilities. The WDA capability is `shouldWaitForQuiescence` (sets `app.fb_shouldWaitForQuiescence`, default YES); others: `eventloopIdleDelaySec`, `appLaunchStateTimeoutSec`, `disableAutomaticScreenshots`, `shouldTerminateApp`, `shouldUseSingletonTestManager`.
- Private timeouts (`FBXCAXClientProxy`, 16.11.0, PR #1233): `withAXTimeout:do:error:` sets `[FBAXClient _setAXTimeout:]` (default 60 s; bounds AX round-trips such as `snapshotForElement`, `attributesForElement`, `activeApplications`); `withXPCRequestTimeout:do:` uses `_XCTSetXPCRequestTimeout` (default 30 s; bounds `XCTRunnerAutomationSession` calls such as `matchesForQuery:`); `withApplicationStateTimeout:do:` uses `_XCTSetApplicationStateTimeout` (default 60 s; bounds quiescence `XCTWaiter` waits and launch/foreground transitions). All three are process-wide and "do NOT cancel the underlying request"; the AX server keeps working on the abandoned snapshot. None is exposed as a setting yet, and `snapshotForElement` is not wrapped by default.
- Process-level flags set at startup: `XCTDisableRemoteQueryEvaluation`, `XCTDisableAttributeKeyPathAnalysis` (`NSUserDefaults`), `XCTestConfiguration.emitOSLogs`, `disableAutomaticScreenshots`. Undocumented by Apple; **unverified** what they save.

## 2. How `/source`, `/wda/accessibleSource` and element routes are built

- `FBDebugCommands.m`: `GET /source` (with or without session) reads `format` (`xml` default, `json`, `description`), `excluded_attributes` (comma list; snake_case, which PokiCore already uses) and `scope` (XML only). No session: root is `XCUIApplication.fb_activeApplication`. `GET /wda/accessibleSource` calls `fb_accessibilityTree`.
- XML: `fb_xmlRepresentationWithOptions:` -> `FBXPath`. It waits `animationCoolOffTimeout` for stability, takes one `fb_standardSnapshot` (public `-[XCUIElement snapshotWithError:]`) of the application, then walks `snapshot.children` recursively with an `@autoreleasepool` per child, writing attributes through libxml2. Attributes not excluded that need extra AX work: `visible` (`fb_isVisible`, resolved from `FB_XCAXAIsVisibleAttribute` if cached in `additionalAttributes`, else a per-element `fb_attributeValue:` call) and `accessible` (`isWDAccessible`, walks ancestors and takes a custom snapshot). Custom actions, min/max, nativeFrame are off unless enabled.
- JSON: `fb_tree:` -> `dictionaryForElement:recursive:excludedAttributes:` which always writes `customActions` via `wdCustomActions` plus the attribute blocks (`visible`, `accessible`, `traits`, ...). The per-element `customActions` resolution is the extra AX round-trip you measured; `pageSourceExcludedAttributes` can drop `customActions` in JSON only from WDA 16.17.6. That explains XML being 3-7x faster.
- Snapshot kinds (`XCUIElement+FBUtilities.m`, `+FBWebDriverAttributes.m`): `fb_standardSnapshot` = `snapshotWithError:`; `fb_customSnapshot` = `fb_query fb_uniqueSnapshotWithError:` using WDA's attribute list (`FBCustomAttributeNames`: `XC_kAXXCAttributeIsVisible`, `IsElement`, min/max, custom actions, resolved from XCTest's `XCAXAccessibilityAttributesForStringAttributes` in `XCTestPrivateSymbols.m`); `fb_nativeSnapshot` = `resolveOrRaiseTestFailure:` (used for `hittable`). `FBXCElementSnapshotWrapper` wraps either so `wd*` accessors work on cached snapshots.
- Both kinds end in `-[XCAXClient_iOS requestSnapshotForElement:attributes:parameters:error:]`, which is an AX IPC to the target app's main thread. There is no documented way to ask XCTest for a snapshot "without quiescence": the quiescence wait is a separate pre-step (`waitForQuiescenceIncludingAnimationsIdle:`) that WDA already swizzles out when `waitForIdleTimeout` is 0 / `shouldWaitForQuiescence` is false. What remains when the app never idles is the AX request itself, served by the app's run loop. Video decoding and CoreAnimation do not by themselves block the main thread, so a stall on JD.com/WeChat is more likely (a) an app main thread saturated by layout/scroll work, (b) a very large tree (snapshot is proportional to element count, 50-100 ms per snapshot on small apps), or (c) the `accessibilityDeadline` pre-check never seeing an idle run loop. Only measurement separates these.

## 3. Alternative or complementary tree sources on the phone, without a Mac

| Source | Under animation | Latency | Completeness | Needs XCTest runner | Crash risk |
|---|---|---|---|---|---|
| WDA XML `/source`, attributes excluded, depth/children capped | Fails only when the app's main thread is saturated; quiescence can be disabled | 0.2-2 s typical, unbounded worst case | Labels, values, frames, types, traits, enabled; `visible`/`accessible` cost extra | Yes | Medium: 60 s AX timeouts queue everything behind them |
| WDA `format=description` (XCTest `debugDescription`) | Same snapshot path, no attribute resolution | Fastest WDA path per Appium | Unstructured text, needs parsing | Yes | Same |
| `/wda/accessibleSource` | Same snapshot plus `isWDAccessible` per node | Slower than XML | Only accessible elements | Yes | Same |
| Direct `XCAXClient_iOS`/AXRuntime calls from the runner process (what WDA's "custom snapshot" already is) | Same AX IPC, same main-thread dependency | Could skip XCTest's query layer; not faster than one snapshot | Full | Yes (the entitlements come from running as an XCTest bundle) | High: private selectors change per iOS; callstack/agent-device keeps ~450 lines of guarded dynamic ObjC for a simulator-only variant |
| idb `accessibility info` | Simulator only (host-side `FBSimulatorAccessibilityCommands`) | Fast | AXLabel, AXFrame, type, traits | No | Not applicable on device |
| `com.apple.accessibility.axAuditDaemon.remoteserver` (pymobiledevice3 `AccessibilityAudit`; RSD shim `...remoteserver.shim.remote` exists per ios-core) | Independent of XCTest quiescence | Per-element: the daemon resolves only the focused element (`deviceInspectorMoveWithOptions:` then `deviceElement:valueForAttribute:`); walking a screen is seconds | Label, identifier, value, caption, frame via attributes; no full tree, no hit-test API | No | Low for the runner, but VoiceOver-style focus moves are visible on screen; reaching the shim from the phone's own tunnel is plausible since Poki already opens RemoteXPC, **unverified** |
| Vision OCR on `/screenshot` (in place) | Yes | 0.1-0.5 s | Text and boxes only; no traits/values/hierarchy | No | None |

WDA XML stays primary, OCR the fallback under stall; the AX audit daemon is not a tree source.

## 4. Why the runner wedges or dies, and how to prevent it

- **Queueing behind a stuck snapshot.** WDA runs routes on one serial queue except `.standalone` ones (`/status`, `/screenshot`, `/health` since 16.15.2). The AX timeout is 60 s process-wide and nothing cancels the server-side request when it elapses (`FBXCAXClientProxy.h`). So one hung `/source` holds the queue for up to 60 s; Appium's troubleshooting page attributes a further 60 s stall to a `testmanagerd` crash while the OS restores it. Mitigation: never pile up reads (PokiCore's `busyWith` guard is right), prefer standalone routes while busy, and ask upstream to expose `withAXTimeout` as a session setting (the wrapper exists since 16.11.0 but is not wired to `/source`).
- **`POST /session` while busy.** `handleCreateSession` kills the previous session; `FBSession.kill` waits up to 35 s for a pending teardown and raises `FBSessionCreationException` "retry the session creation later". With `shouldTerminateApp` true it also terminates the previous app under test. Create one session with no `bundleId`, keep it, and reuse it.
- **Memory.** XML generation uses an `@autoreleasepool` per child (`FBXPath`), 9.0.5 added pools to drain temporaries, 16.13.0 releases LRU cache values. Memory is proportional to tree size times attributes; `snapshotMaxDepth`/`snapshotMaxChildren` are the documented knobs ("may help to prevent out of memory or timeout errors"). No jetsam report found in WDA issues; **unverified** that jetsam is what kills your runner. Check `JetsamEvent-*.ips` on the phone.
- **XCTest execution-time allowance.** Default 600 s per test and off unless `-test-timeouts-enabled YES` or the test plan enables it; WDA's single test method runs for the server's whole life, so leave timeouts disabled in the xctestrun/launch config. `-maximum-test-execution-time-allowance` caps what a test may request. (Apple `XCTestCase.executionTimeAllowance`; simplified.guide.)
- **Developer connection drop.** testmanagerd logs "Considering exiting, N test sessions ... does not have control session" when the IDE connection closes, and in a captured session the runner was reported "Failed to background test runner" about 30 s after the DTX disconnect. Appium users on iOS 17 report automation "immediately stops when iPhone is disconnected". pymobiledevice3's `xcuitest.py` blocks on the main DTX connection and closes the control and session proxies when it exits; it has no keepalive and no reconnect, and `ios-core` exposes none. Conclusion: the control session must stay open for the runner's lifetime; the 25-30 s you see matches testmanagerd's grace. No reconnect path is documented; relaunch is the recovery.
- **iOS 17+ session model.** Service `com.apple.dt.testmanagerd.remote` over RSD (lockdown: `com.apple.testmanagerd.lockdown.secure`), `_IDE_initiateControlSessionWithCapabilities:` on 17+, launch through DVT ProcessControl, `authorize_test` by PID, then `start_executing_test_plan`. Runner bundles must not embed `Frameworks/XC*` or the process crashes without `xcodebuild`. On iOS/tvOS 27 Appium disabled the `devicectl` fallback (12.5.1) because a runner launched that way "may stay in the foreground and never start its HTTP server", and a broken RemoteXPC tunnel now fails fast. The "Automation Running" overlay and passcode prompt on session start are XCTest limitations.
- **Appium's own keep-alive.** None at the XCTest level: `wdaStartupRetries` (1 on devices), `wdaLaunchTimeout` 60 s, `wdaConnectionTimeout` 240 s, `useNewWDA` reinstall, `shouldTerminateApp`, `wdaEventloopIdleDelay` (sets `eventLoopHasIdledDelay`, default 0), `disableAutomaticScreenshots` true, `skipLogCapture`, `mjpegServerPort` 9100. Appium keeps `xcodebuild` (its control session) alive for the whole server life, which is the only reason WDA survives hours.
- **Known crash classes.** Quiescence selector changes per Xcode (8.9.1); `accessibilityDeadline` crashing WebContent (#1290, fixed 16.14.1); stability overrides leaking after an exception (16.13.6).

## 5. Keeping tree and screenshot consistent

- WDA's `/screenshot` is `-[FBScreenshot takeInOriginalResolutionWithQuality:]`: `XCTScreenshotRequest` sent through `FBXCTestDaemonsProxy testRunnerProxy` `_XCT_requestScreenshot:withReply:` with a 20 s semaphore, no quiescence wait. `/source` is an AX snapshot of the app's main thread. They are two IPCs to two processes (testmanagerd/screen capture vs the app's AX server) and nothing orders them; a mismatch is expected whenever the screen changes between them, and even a single snapshot can carry stale frames during live layout changes (Apple forum 847880).
- There is no XCTest call that returns snapshot and pixels together. `XCUIElement.screenshot` takes a snapshot to find the frame and then a screenshot, in that order, still two steps.
- What others do: Appelium takes one whole-app snapshot and treats it as the atomic truth for all checks; they do not pair it with pixels. The MJPEG stream (`mjpegServerFramerate` 10, `mjpegServerScreenshotQuality` 25) gives frames with arrival times, which is the cheapest way to bracket a read.
- Recommended for PokiCore: issue `/screenshot` (standalone, not queued) immediately before `/source`, record both wall-clock spans, and on return compare a cheap screen hash of a second `/screenshot` taken right after the tree; if the two frames differ beyond a threshold, mark the reading `moving` and let the model rely on element text rather than coordinates, or re-read once. Timestamps alone cannot prove consistency because neither IPC reports when it sampled.
